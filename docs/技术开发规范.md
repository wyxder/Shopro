# Shopro AI 技术开发规范

> 版本：v1.0 ｜ 生效日期：2026-10-30 ｜ 维护人：项目负责人
> 适用范围：`src/`（商家创作端）、`supabase/`（Edge Functions 与迁移）、`api/`（AI 网关）、`backend/`（厂商运营后台）、`docs/`（文档）
> 配套文件：[Rules.md](../Rules.md)（强制红线速查）、[AGENTS.md](../AGENTS.md)（协作与提交约束）

## 0. 规范等级与基本约定

| 等级 | 含义 | 违反后果 |
|---|---|---|
| **必须（MUST）** | 红线，自动化或评审强制拦截 | 阻断合入 |
| **应该（SHOULD）** | 默认做法，偏离需在 PR 说明理由 | 评审要求补充说明 |
| **建议（MAY）** | 优化项，不做不阻塞 | 记录为技术债 |

**基本原则**

1. **钱、权限、任务状态是核心路径**：必须手写、必须评审、必须有日志。
2. **先有契约再有实现**：接口字段、错误码、状态枚举先定，再写逻辑。
3. **不做无依据的兜底**：能确定不会发生的分支不写防御代码；边界处（用户输入、第三方 API、支付回调）必须校验。
4. **不引入未使用的抽象**：一个场景一个实现，出现第二次重复才考虑抽取。

## 1. 工程与仓库规范

### 1.1 工具链基线

| 项 | 约定 |
|---|---|
| 包管理器 | **pnpm 10**，禁止 npm / yarn 混用；`pnpm-lock.yaml` 必须提交 |
| Node / TS | TypeScript 5.x；路径别名统一 `@/* → src/*` |
| 代码检查 | `biome 2.4.5`（lint 开启，formatter 关闭）+ `ast-grep` 自定义规则 |
| 类型检查 | `tsgo -p tsconfig.check.json`（开启 `strictNullChecks`，排除 `src/components/ui`） |
| 提交前门禁 | **必须**执行 `pnpm lint`（详见 2.10），五项全绿才允许提交 |

### 1.2 目录职责（新增文件必须落在对应目录，禁止随意新建顶层目录）

| 目录 | 职责 | 禁止 |
|---|---|---|
| `src/pages/` | 页面级业务编排，文件名 `XxxPage.tsx` | 放通用组件、放裸 SQL |
| `src/components/` | 业务公共组件；`ui/` 为无业务原子组件 | 在 `ui/` 写业务逻辑 |
| `src/api/` | 统一数据访问层，按领域拆文件（`credits.ts`/`video.ts`/`products.ts`） | 页面直接 `createClient` 或拼 URL |
| `src/hooks/` | 可复用状态与副作用（`use-*.ts`/`useCredits.ts`） | 存放业务页面逻辑 |
| `src/lib/` | 无 UI 的纯工具与协议封装（SEE、媒体、模型适配） | 依赖 React 组件 |
| `supabase/functions/` | Edge Functions，一个能力一个函数；公共逻辑进 `_shared/` | 跨函数复制粘贴公共代码 |
| `supabase/migrations/` | 增量迁移，格式 `000NN_描述.sql` | 直接改历史迁移文件 |
| `api/` | Python AI 网关（Vercel Serverless） | 在此写业务入库逻辑 |
| `backend/` | 厂商运营后台（Vue 3 + Spring Boot REST） | 与创作端逻辑耦合 |
| `docs/` | 规范、架构、PRD、测试文档 | 放临时脚本与调试产物 |

### 1.3 命名约定

| 对象 | 规则 | 示例 |
|---|---|---|
| 组件 / 页面 | PascalCase，页面后缀 `Page` | `VideoEditPage.tsx`、`UrlProductImportDialog.tsx` |
| Hook | camelCase，`use` 前缀 | `useCredits.ts`、`useDraft.ts` |
| 工具/服务 | camelCase | `creditGuard.ts`、`sse.ts`、`videoFrame.ts` |
| 类型/接口 | PascalCase，禁止 `I` 前缀 | `ApiResponse<T>`、`TrackItem` |
| 常量 | UPPER_SNAKE | `AUDIO_TRACKS`、`ALLOWED_ORIGINS` |
| Edge Function | kebab-case 目录名，能力命名 | `seedance/`、`stepaudio/`、`alipay-payment-notify/` |
| 数据库表/列 | snake_case，复数表名 | `user_plans`、`credit_logs`、`created_at` |
| RPC | 动词_名词 | `deduct_credits`、`refund_credits`、`redeem_coupon` |
| 环境变量 | UPPER_SNAKE，按厂商前缀 | `SUPABASE_SERVICE_ROLE_KEY`、`VECTRUST_API_KEY` |

### 1.4 分支、提交与环境

- 分支：`feature/<模块>-<简述>`、`fix/<问题>-<简述>`，禁止直接在 `master` 提交业务改动。
- 提交：中文、说明“改了什么模块 + 为什么”；**禁止使用“完善”，统一用“新增”表述**（与 [AGENTS.md](../AGENTS.md) 一致）。
- 环境变量：新增变量必须同步 `.env.example`；**禁止**将真实密钥写入代码、注释、日志、文档或前端。
- 依赖：新增依赖需在 PR 说明用途与体积影响；能复用现有依赖（`ky`/`zod`/`date-fns`）不新装。

## 2. 前端开发规范

### 2.1 技术边界

React 18 + TypeScript + Vite + Tailwind + Radix（shadcn 风格）+ Framer Motion + React Query + Supabase JS。
**不得**引入第二套 UI 框架、第二套状态容器或第二套请求库。

### 2.2 类型规范

- 新代码必须在 `tsgo -p tsconfig.check.json` 下通过（`strictNullChecks: true`）。
- `any` 仅允许出现在“对接第三方原始响应”的边界，且**必须**在 3 行内收窄为业务类型。
- 接口返回统一使用 `ApiResponse<T>`（`src/api/client.ts`），禁止页面自行定义 `{ code, data }` 变体。
- 公共类型放 `src/types/`；组件内部 Props 就近定义并导出，禁止匿名内联对象重复声明。
- 枚举值使用字面量联合类型（如 `RedeemCode`），禁止散落魔法字符串。

### 2.3 组件规范

- 页面只做编排：取数 → 组合组件 → 提交动作；单个页面文件建议 ≤ 800 行，超出按“区块组件”拆分。
- `components/ui/` 只允许无业务原子组件；业务组件放 `components/`。
- Props 必须显式类型；回调命名 `onXxx`；布尔值 `isXxx/hasXxx`。
- 副作用只放 `useEffect`，且必须有清理函数（订阅、定时器、AbortController、事件监听）。
- 禁止在渲染期发起请求或写全局状态。

### 2.4 数据访问规范

- **所有** Supabase / HTTP 调用必须经 `src/api/*.ts`，并通过 `handleApiRequest` 归一化：

```ts
export async function fetchUserCredits(userId: string): Promise<ApiResponse<UserCreditsInfo>> {
  return handleApiRequest(async () => {
    const res = await supabase.from('user_plans').select('...').eq('user_id', userId).maybeSingle();
    if (res.error) return { data: null, error: res.error };
    return { data: mapToCreditsInfo(res.data), error: null };
  });
}
```

- 页面禁止 `try/catch` 吞异常后无提示；错误文案统一中文、面向用户、不暴露堆栈与内部字段。
- React Query：`queryKey` 统一 `[领域, 动作, 参数]`（如 `['credits','detail',userId]`）；写操作后显式 `invalidateQueries`，禁止依赖轮询自愈。
- 认证态只从 `AuthContext` 读取，禁止在组件内直接读 localStorage 的 token。

### 2.5 交互与 UI 硬规则（`ast-grep` 自动拦截，见 `.rules/`）

| 规则 | 要求 |
|---|---|
| Button 可交互 | `<Button>` 必须有 `onClick` / `type="submit|reset"` / `asChild`，或位于 `*Trigger`、`<Link>`、`<a>` 内 |
| 对比度 | `variant="outline"` 禁止配 `text-foreground`、`text-white`、`text-gray-*`；默认 variant 禁止加 `text-primary` |
| SelectItem | 禁止 `value=""`；全选场景用 `all` 等具名值 |
| Toast | 统一 `import { toast } from "sonner"`，禁止 `@/hooks/use-toast` |
| Slot 嵌套 | Radix `*Trigger asChild` 内禁止包 `FormControl`（会导致点击失效） |
| 登录 | Google 登录统一 `signInWithSSO`，禁止 `signInWithOAuth({ provider: 'google' })` |

### 2.6 样式规范

- 优先 Tailwind 原子类；重复三次以上的样式组合才抽组件类。
- 颜色/圆角/阴影必须使用 `index.css` 中的主题变量（玻璃态体系），禁止散落硬编码色值。
- 必须适配 375px / 768px / 1440px 三档；暗色与浅色主题均需自查对比度。
- 动画：Framer Motion 只动 `transform` / `opacity`；禁止动画 `width/height/top/left`。

### 2.7 长任务与流式交互

- 文本流式统一走 `src/lib/sse.ts` 封装（`eventsource-parser`），禁止各页面自写解析。
- 视频等长任务：提交拿 `request_id` → 轮询查询；轮询间隔采用退避（如 2s→4s→8s，上限 30s），必须有最大次数与超时。
- 组件卸载必须取消在途请求（`AbortController` 或标记位），避免卸载后 setState。

### 2.8 性能规范

- 长列表（作品/素材/日志）超过 100 条必须虚拟化或分页。
- 拖拽/时间轴交互：拖拽过程用 motion value 或 ref 更新，**松手才提交 React state**。
- 大图/视频预览使用缩略图或代理文件，禁止在时间轴内直接加载原片。
- 计算密集逻辑（时间↔像素换算、吸附候选）使用 `useMemo` 并纳入依赖；禁止在 render 内创建大数组。

### 2.9 可访问性与文案

- 图标按钮必须带 `aria-label`；表单控件必须有 `label` 或 `aria-labelledby`。
- 文案统一简体中文，金额/积分必须带单位；危险操作（删除、退款、清空轨道）必须二次确认。

### 2.10 质量门禁（提交前必须全绿）

```bash
pnpm lint   # = tsgo 类型检查 + biome lint + .rules/check.sh + tailwind 构建校验 + .rules/testBuild.sh
```

五项中任意一项失败，**禁止提交**；不得通过注释规则、改 `tsconfig` 排除目录等方式绕过。

## 3. 后端开发规范

### 3.1 服务边界

| 层 | 承载 | 关键约束 |
|---|---|---|
| Supabase Edge Functions（Deno，22 个） | 标准能力：认证校验、AI 编排入口、支付回调、短信、团队接口 | 单函数单一职责；短时任务；公共逻辑进 `_shared/` |
| FastAPI / ASGI 网关（`api/`） | 多模型密钥隔离与透传、MCP 工具契约 | 必须鉴权；禁止成为公网裸代理 |
| Spring Boot REST（`backend/`） | 厂商运营后台 `/api/admin/**` | RBAC、审计、只读聚合优先 |
| PostgreSQL（Supabase） | 业务数据、RLS、RPC | 金额/积分变更只走 RPC |

### 3.2 Edge Function 强制模板

每个函数**必须**按以下顺序实现（参考 `supabase/functions/seedance/index.ts`）：

1. `OPTIONS` 预检返回（CORS）；
2. 方法校验，非法方法 `405`；
3. JWT 校验（`authenticateRequest`），失败 `401`；
4. `req.json()` 解析失败 `400`；
5. `action` 白名单校验，非法 `400`；
6. 密钥存在性校验，缺失 **`503`**（禁止明文兜底）；
7. 业务执行，统一 `jsonResponse` / `errorResponse` 输出。

```ts
// _shared 统一出口
import { authenticateRequest } from '../_shared/auth.ts';
import { errorResponse, jsonResponse, unauthorizedResponse } from '../_shared/errors.ts';
import { handleCorsPreflight } from '../_shared/cors.ts';

Deno.serve(async (req) => {
  const preflight = handleCorsPreflight(req);
  if (preflight) return preflight;
  if (req.method !== 'POST') return errorResponse('Method Not Allowed', 405, 4050, req);

  const auth = await authenticateRequest(req);
  if (!auth.userId) return unauthorizedResponse(auth.error ?? undefined, req);

  const { action, ...payload } = await req.json().catch(() => ({}));
  if (!['create', 'query'].includes(action)) return errorResponse('非法 action', 400, 4000, req);
  // ... 业务
});
```

- `GET` 请求**禁止**携带 body，参数必须拼在 URL 上（`.rules/supabase-edge-function-get-body.yml`）。
- CORS 白名单只允许 `cors.ts` 中登记的域名；新增域名须走评审，禁止 `*` 通配到生产。
- 函数内禁止硬编码密钥、上游 URL、回调地址；一律 `Deno.env.get()`。

### 3.3 响应契约

| 场景 | 结构 | 说明 |
|---|---|---|
| 运营后台 REST | `{ code, message, data, traceId }` + 分页 `PageResult<T>` | `code=0` 成功，非 0 为业务错误码 |
| Edge Function | `{ error, code, success: false }` / 业务数据 | 4xx/5xx 语义明确 |
| 前端归一化 | `ApiResponse<T> = { data, error, success, status }` | 页面只消费这一种结构 |

错误码分段：`400x` 参数、`401x` 鉴权、`403x` 权限、`409x` 冲突/幂等、`429x` 限流、`500x` 上游与内部。**禁止**把上游原始错误体直接返回给前端。

### 3.4 认证与授权

- 一律以 JWT 中的 `auth.uid()` 作为用户身份，**禁止**信任请求体里的 `user_id`。
- `service_role` 仅用于服务端内部任务与退款等特权操作，必须显式判定（见 `_shared/auth.ts` 的 `isServiceRole`）。
- 数据库必须开启 RLS；新表默认“拒绝所有”，再按角色最小授权。
- 运营后台接口按 RBAC 校验角色，越权返回 `403` 并写审计日志。

### 3.5 数据库规范

- 迁移：新增 `supabase/migrations/000NN_描述.sql`，只增不改；一次迁移只做一件事；必须可在空库顺序执行。
- 表：必须有 `id`（uuid）、`created_at`（timestamptz，UTC）、必要的外键与索引；软删除用 `deleted_at`，禁止物理删除业务数据。
- 金额/积分：整数最小单位存储，**禁止**浮点；余额字段与流水表 `credit_logs` 必须同时更新。
- 变更余额只能通过 `SECURITY DEFINER` RPC：

```sql
-- 唯一原子路径：行锁 + 余额校验 + 流水写入，同一事务内完成
SELECT credits_total, credits_used FROM user_plans WHERE user_id = p_user_id FOR UPDATE;
```

- 退款/冲正只写反向流水（`REVERSAL`），**禁止**直接改余额或删除流水；退款 RPC 仅 `service_role` 可调。
- 向量检索使用 pgvector，索引按业务域（品类/语种）分表或分命名空间，禁止全库无过滤 Top-K。

### 3.6 事务、幂等与状态机

- 任何“扣减/发放/退款/订单状态变更”必须满足：**幂等键**（订单号、`request_id`、业务唯一键）+ **状态机单向流转**。
- 长任务状态：`pending → queued → running → succeeded / failed → refunding → refunded`；非法流转拒绝并记录。
- 重试必须有上限与退避；重试不得重复扣费。

### 3.7 支付规范

- 回调必须验签 + 校验金额与订单号；重复回调按幂等返回成功。
- 金额单位、币种、订单快照（套餐版本/价格）必须落库，禁止用“当前配置”回算历史订单。
- 支付相关日志脱敏：不打印完整签名、密钥、手机号、身份证。

### 3.8 日志与可观测

- 每个请求带 `traceId`，贯穿前端 → Edge → 上游模型 → 数据库。
- 每次 AI 调用写 **Attempt** 记录：入参摘要、出参摘要、耗时、错误码、消耗积分、模型名与版本。
- 日志分级：`error`（需人工介入）、`warn`（可自愈/降级）、`info`（业务节点）；禁止 `console.log` 打印完整 Prompt 或用户隐私。

### 3.9 限流、配额与成本

- 按用户维度限制调用频次与并发；单次请求设最大 token / 时长 / 分辨率上限。
- 上游失败按策略降级（备用模型/备用通道），连续失败触发熔断。
- 每次模型调用必须记录成本字段，便于对账与定价。

### 3.10 Python 网关（`api/`）

- 必须校验调用方凭据（`DXKP_GATEWAY_TOKEN` / `MCP_API_KEY`），未配置时**拒绝服务**而非放行。
- 只做协议转换与密钥注入，不写业务入库；上游超时必须设置（建议 60s 文本、180s 视频提交）。
- 透传时白名单化路径与请求头，禁止任意 header 透传。

## 4. Agent / AI 服务规范

### 4.1 分层架构

```
接入层（Edge Functions / FastAPI 网关）  ← 鉴权、限流、参数校验、密钥隔离
        ↓
编排层（Workflow 状态机）               ← 节点、条件边、重试、断点、Attempt
        ↓
能力层（模型 Provider）                 ← 文本 / 视频 / 语音 / 图像，可切换可降级
        ↓
资产层（Prompt / 知识库 / 爆款话术）     ← 版本化、可检索、可评估
```

**约束**：上层不得直接调用模型厂商 SDK；模型只能由能力层访问；编排层不得依赖具体模型名写死分支。

### 4.2 模型接入规范

- 每个能力实现 `Provider` 接口（`generate` / `submit` / `query`），通过配置切换模型，业务代码不变。
- 必须实现：超时、重试（有上限）、降级（备用模型）、成本计量、错误归一化。
- 模型版本必须与线上实际一致并可追溯（记录 `model`、`version`、`provider`、`request_id`）。
- 新增模型/新版本：先在灰度环境跑通评测集，再切流量；禁止直接改线上常量。

### 4.3 Prompt 规范

- Prompt 入库管理：唯一 ID + 版本号 + 适用场景标签 + 变更记录；线上只引用版本号。
- 结构化输出必须使用 JSON Schema 约束，解析失败进入“重试一次 → 降级模板”链路。
- 温度分级：创意类偏高、结构化抽取偏低；同一 Prompt 的温度与模型必须随版本固定。
- 防注入：用户输入只进入“数据槽位”，**禁止**拼接进系统指令；检索内容需标注来源与边界。
- 长度预算：单次上下文设上限，超出先摘要或裁剪，禁止无限堆历史。

### 4.4 RAG 规范

- 文档切分按语义段落（建议 300–800 字），保留来源元数据（商品 ID、语种、品类、时间）。
- Embedding 与检索模型版本固定并记录；换模型必须重建索引。
- 检索必须带业务过滤（品类/语种/租户），Top-K 默认 5，禁止无过滤全库召回。
- 召回质量用两类指标评估：人工抽检相关性、生成采纳率；低采纳内容不进入优选池。

### 4.5 长任务编排

- 统一 `submit → request_id → query` 两段式；状态持久化到数据库，禁止放内存。
- 每次尝试生成 `attempt_id`；失败按 `retryable` 标记决定重试；最终失败自动触发积分冲正。
- 幂等：同一 `request_id` 重复查询不得重复扣费；同一业务请求重复提交返回原任务。
- 超时策略：提交超时、查询超时、总时长上限三层都要有。

### 4.6 数字人语音与情感链路

情感标注必须是**结构化、可复现**的数据，不得只存在于 Prompt 文本：

```ts
interface EmotionSegment {
  index: number;        // 句序
  text: string;         // 该句文本
  emotion: 'excited' | 'urgent' | 'trust' | 'friendly' | 'neutral';
  intensity: 0 | 1 | 2; // 强度档位
  startMs: number;
  endMs: number;
}
```

- 下游映射必须确定性：`emotion + intensity` → TTS `instruction` 模板 → 数字人表情/姿态关键帧。
- 同一段文案 + 同一标注，必须得到同一参数（可回归测试）。
- 语音合成文本必须与字幕文本同源，禁止两份文案漂移。

### 4.7 内容安全与合规

- 生成内容必须过敏感词与违规内容检查；命中即拦截并记录证据链。
- 数字人形象/声音必须有授权来源记录；导出视频按配置加水印。
- 用户上传素材需校验类型与大小，禁止直接公网可读的私有素材。

### 4.8 评估与迭代

- 每个 AI 能力维护一个离线评测集（≥ 30 条真实样例），改动 Prompt/模型必须回归。
- 线上指标：成功率、P95 时延、单条成本、用户采纳率、失败退款率；任一项劣化 > 10% 触发回滚。
- A/B 实验必须固定分流比例与观测窗口，结论落文档。

### 4.9 开放能力（MCP / OpenAPI）

- 工具契约（入参/出参/错误码）与内部实现解耦，对外只暴露必要字段。
- 外部调用必须鉴权 + 限流 + 配额；禁止暴露内部表名与服务角色密钥。

## 5. 安全与合规

| 项 | 要求 |
|---|---|
| 密钥 | 仅存服务端环境变量；前端只持有 anon key；日志/文档/截图禁止出现密钥 |
| 数据隔离 | 所有业务表启用 RLS；跨租户查询必须显式带租户条件 |
| 输入校验 | 所有外部输入（URL、CSV、JSON、回调）必须做类型、长度、枚举校验 |
| 上传 | 限制 MIME 与大小；私有文件禁止公开桶 |
| 前端安全 | 禁止 `dangerouslySetInnerHTML` 渲染用户内容；外链 `rel="noopener noreferrer"` |
| 日志 | 手机号/邮箱/身份信息脱敏；Prompt 与素材 URL 按需截断 |
| 依赖 | 高危漏洞必须修复；新增依赖需评审 |
| 合规 | 肖像与声音授权、生成内容标识、隐私政策与数据删除能力 |

## 6. 测试与发布

### 6.1 测试分层

| 层 | 范围 | 要求 |
|---|---|---|
| 静态 | 类型、lint、ast-grep、构建 | 每次提交必须通过 |
| 单元 | 金额/积分换算、时间轴换算、状态机、解析器 | 核心路径必须有 |
| 契约 | 前端 ↔ Edge ↔ 上游字段 | 改字段必须同步更新 |
| 冒烟 | 登录 → 选品 → 生成 → 扣费 → 冲正 → 支付 | 上线前必跑 |

### 6.2 发布流程

1. 本地 `pnpm lint` + 冒烟通过；
2. 数据库迁移先在测试库顺序执行，确认可重复；
3. Edge Functions 先部署灰度，验证 401/503/正常路径；
4. 前端发布后核对：登录、扣费、生成、支付回调四条主链路；
5. 保留回滚方案（前端版本回滚、函数版本回滚、迁移只增不删保证兼容）。

### 6.3 上线后监控

- 关键告警：生成失败率、退款率、支付回调失败、Edge 5xx、上游超时。
- 每日对账：积分发放/消耗/冲正总额与订单金额一致。

## 7. 协作与代码评审

### 7.1 PR 规范

- 一个 PR 只做一件事；标题说明模块与目的；描述包含“改了什么 / 为什么 / 怎么验证”。
- 涉及钱、权限、迁移、支付、模型切换的 PR 必须双人评审。

### 7.2 评审清单

- [ ] 是否有未处理的边界输入与失败分支
- [ ] 是否绕过统一 API 层 / 直接操作余额
- [ ] 是否新增硬编码密钥、域名、模型名
- [ ] 是否补充日志与错误码
- [ ] 是否影响既有契约（字段/枚举/错误码）
- [ ] 数据库迁移是否只增不改、是否含 RLS
- [ ] 是否有性能风险（大列表、每帧状态更新、无上限轮询）

### 7.3 AI 生成代码规范

- **AI 写边缘，人守核心**：UI、样板、文档可借助 AI；事务、权限、支付、状态机、扣费必须人工编写与逐行确认。
- AI 生成代码必须通过同一套门禁，不得降低检查标准。
- 提交前必须自查：是否存在幻觉 API、未使用依赖、重复工具函数、错误的中文文案。
