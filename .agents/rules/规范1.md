# 通用技术开发规范（企业版）

> 适用范围：前后端、移动端、Agent 与大模型应用、基础设施与数据服务。
> 目标：让规范可执行、可度量、可审计，而不是停留在"注意代码质量"的口号。

---

## 0. 文档说明

### 0.1 规则等级

| 等级 | 含义 | 违反后果 |
|---|---|---|
| **MUST（必须）** | 强制项，CI 或评审必须拦截 | 阻塞合入/发布 |
| **SHOULD（应当）** | 默认执行，偏离需在 PR 中说明理由 | 评审记录豁免原因 |
| **MAY（可以）** | 可选最佳实践 | 无 |

### 0.2 度量原则

- 能被工具判定的规则，一律交给 CI，人不重复检查；
- 不能被工具判定的规则，必须给出可勾选的评审清单；
- 每条规则都要有验收标准，否则不写进规范。

### 0.3 例外与豁免

1. 安全、合规类规则**不设例外**；
2. 其他规则如需豁免，在 PR 中标注 `[waiver] 规则编号 + 原因 + 失效时间`；
3. 豁免超过 30 天未关闭，升级为技术债并纳入季度治理。

## 1. 总则

### 1.1 五条工程原则

1. **正确性优先**：边界、异常、并发、幂等先想清楚，再谈优雅。
2. **一致性优先于个人偏好**：同一仓库只有一套风格，工具决定格式。
3. **可读性优先于技巧**：代码是写给人看的，顺便让机器执行。
4. **小步快跑**：小提交、小 PR、小发布，任何一步都可回滚。
5. **可观测**：没有日志、指标、追踪的功能视为未完成。

### 1.2 技术债管理

- 新增技术债必须登记（issue + 影响面 + 偿还计划）；
- 禁止以"以后再优化"为由跳过安全与测试门禁；
- 每个迭代预留不少于 10% 产能用于债务与稳定性治理。

## 2. 编码规范

### 2.1 通用硬规则（MUST）

1. **禁止提交密钥、Token、证书、生产配置**；
2. **禁止吞异常**：捕获后必须处理、转换或记录，不允许空 catch；
3. **禁止魔法值**：状态码、阈值、路径必须常量化或配置化；
4. **禁止在循环内做远程调用**（N+1），批量接口优先；
5. **公共函数必须声明输入输出契约**（类型、可空性、错误语义）；
6. **单函数不超过 50 行、圈复杂度不超过 10**（超出需拆分或说明）；
7. **单文件不超过 800 行**，超出按职责拆分模块；
8. **禁止复制粘贴超过 10 行的重复逻辑**，抽公共实现；
9. **时间统一使用 UTC 存储、按用户时区展示**；
10. **金额禁用浮点**，统一最小货币单位（分）或定点小数。

### 2.2 命名与结构

| 对象 | 规则 | 示例 |
|---|---|---|
| 包/模块 | 小写单词，语义完整 | `billing`、`orderledger` |
| 类/组件 | PascalCase | `OrderTimeline` |
| 函数/变量 | camelCase / snake_case（按语言） | `deductCredits`、`deduct_credits` |
| 常量 | UPPER_SNAKE | `MAX_RETRY_TIMES` |
| 布尔 | 以 `is/has/can/should` 开头 | `isPaid`、`canRetry` |
| 接口 | 表达能力，不用 `I` 前缀 | `PaymentGateway` |
| 测试文件 | 与被测文件同名 + `.test`/`_test` | `order.service.test.ts` |

**反例**：`data`、`temp`、`obj`、`list1`、`doSomething()`、`SelectV2`（用版本号掩盖语义差异）。
**正例**：`activeSubscriptions`、`SelectWithCheckAll`、`refundOrder()`。

### 2.3 错误处理与日志

- 错误分层：基础设施错误 → 领域错误 → 用户可见错误，逐层转换并保留 cause；
- 对外错误不暴露堆栈、SQL、内部路径；
- 日志必须结构化（JSON），包含 `trace_id`、`user_id`（脱敏）、`module`、`duration_ms`；
- 日志级别：`ERROR` 仅用于需要人介入的异常，业务拒绝用 `WARN`，高频路径用 `DEBUG`；
- 禁止在日志中打印完整手机号、身份证、银行卡、Token、Prompt 中的用户隐私。

```ts
// 反例
try { await pay(order); } catch (e) {}

// 正例
try {
  await pay(order);
} catch (err) {
  logger.error({ traceId, orderId: order.id, err }, 'payment failed');
  throw new PaymentError('PAYMENT_FAILED', { cause: err });
}
```

### 2.4 技术栈差异化适配

| 技术栈 | 必须执行 | 关键差异 |
|---|---|---|
| 后端 Go | `gofmt/gofumpt` + `go vet` + `staticcheck`；错误用 `%w` 包装；goroutine 必须有退出路径 | 并发安全、context 全链路透传 |
| 后端 Java | `google-java-format` + Checkstyle + SpotBugs；Controller 不写业务逻辑 | 事务边界、N+1、线程池隔离 |
| 前端 TS/React | ESLint + Prettier + 严格 TS；组件 props 必须有类型；禁止 `any` | 渲染副作用、状态归属、可访问性 |
| 移动端 iOS/Android | 官方格式化 + 静态分析；主线程禁止 IO；页面必须有加载/空/错误三态 | 内存、启动耗时、弱网、权限 |
| Agent/LLM（Python） | Black/Ruff + 类型注解；Prompt 版本化；工具调用有超时与重试上限 | 非确定性、成本、幻觉、越权调用 |
| SQL/数据 | 迁移脚本可回滚；禁止无索引的大表扫描；禁止在事务中调用外部服务 | 锁范围、幂等、数据一致性 |

### 2.5 正反例对比

| 场景 | 反例 | 正例 |
|---|---|---|
| 参数校验 | 在业务深处才发现参数缺失 | 在入口层统一校验并返回明确错误码 |
| 时间处理 | `new Date('2026-01-01')` 依赖本地时区 | 显式时区或统一 UTC 时间戳 |
| 金额 | `0.1 + 0.2` 浮点累加 | 以"分"为整数计算 |
| 分页 | `SELECT * FROM orders` 全量返回 | 游标分页 + 上限 100 条 |
| 重试 | 失败立即无限重试 | 指数退避 + 最大次数 + 幂等键 |

### 2.6 验收标准

```text
□ 格式化与 lint 零错误（新增代码）
□ 静态分析无高危告警
□ 圈复杂度、函数长度、文件长度达标
□ 无硬编码密钥与魔法值
□ 关键路径日志含 trace_id 且脱敏
□ Code Review 通过命名与结构检查项
```

## 3. 版本控制规范

### 3.1 分支模型（默认 Trunk-Based）

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 始终可发布 | 永久 |
| `feature/*` | 单功能开发 | ≤ 5 天，超期需拆分 |
| `bugfix/*` | 缺陷修复 | ≤ 2 天 |
| `release/x.y` | 版本冻结与补丁 | 随版本退役 |
| `hotfix/*` | 线上紧急修复 | ≤ 24 小时 |

**MUST**：

- 禁止直接 push 到 `main`/`release`；
- 分支名使用白名单前缀，禁止 `dev`、`test1`、人名分支；
- 长期分支每日 rebase 主干，冲突当天解决；
- 发布分支只接受 cherry-pick，不接受新功能。

### 3.2 提交信息（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 用途 |
|---|---|
| feat | 新功能 |
| fix | 缺陷修复 |
| perf | 性能优化 |
| refactor | 重构（行为不变） |
| test / docs / build / ci / chore | 测试、文档、构建、流水线、杂项 |

```text
feat(billing): 支持积分加油包微信直充

- 新增套餐配置与下单接口
- 回调按 out_trade_no 幂等处理
- 失败时冲正已扣积分

Refs: #128
```

**反例**：`update`、`fix bug`、`修改`、`提交一下`、一次提交混合格式化与功能改动。

### 3.3 变更粒度

- 单 PR 变更行数 **≤ 400 行**（不含生成代码与测试），超出必须拆分；
- 重构与功能改动分开提交；
- 生成文件（锁文件、协议代码）单独提交并注明生成命令。

### 3.4 版本与标签

- 公共库遵循 **SemVer**：`MAJOR.MINOR.PATCH`；
- 破坏性变更必须写 `BREAKING CHANGE` 与迁移指南；
- 发布打 annotated tag：`v1.4.2`，附变更摘要；
- 应用服务使用"版本号 + 提交 SHA"双标识，便于回溯。

### 3.5 分支保护（MUST）

```text
□ 禁止 force push 与删除
□ 必须 PR 合入，至少 1 名 owner 批准
□ CI 全绿（lint / test / build / security）
□ 合入前必须与主干同步并重跑流水线
□ 默认 Squash Merge，保持主干线性
```

### 3.6 验收标准

```text
□ 提交信息 100% 符合 type(scope): subject
□ 无超大 PR（>400 行需拆分说明）
□ 主干历史线性、可回滚
□ 每次发布有 tag、CHANGELOG 与回滚点
```

## 4. 代码评审规范

### 4.1 评审范围

**必须评审**：业务逻辑、接口契约、数据模型、权限校验、并发与事务、配置变更、依赖升级、Prompt 与模型调用逻辑、数据库迁移。

**可豁免**：纯格式化、生成代码、文案修改（仍需 1 人 quick approve）。

### 4.2 流程与时效

| 环节 | 要求 |
|---|---|
| 发起 | 先关联 issue；描述含背景、方案、影响面、验证证据 |
| 自评 | 作者先自审 diff，清理调试代码与临时文件 |
| 响应 | 首次评审 ≤ 4 工作小时；超时升级至 owner |
| 争议 | 两轮未达成一致转会议，结论回写 PR |
| 合入 | 所有 `[blocking]` 关闭 + CI 绿 + owner 批准 |

### 4.3 评审清单（MUST 逐项确认）

```text
□ 正确性：边界、空值、异常、并发、幂等
□ 设计：职责边界、依赖方向、是否过度设计
□ 测试：新增逻辑有测试，覆盖失败路径
□ 安全：鉴权、输入校验、敏感数据、越权
□ 性能：N+1、全表扫描、同步外部调用、无界队列
□ 可观测：日志、指标、告警、追踪
□ 兼容：接口/数据结构变更是否向后兼容
□ 文档：用户可见变更是否同步
```

### 4.4 评论分级

| 标记 | 含义 | 是否阻塞 |
|---|---|---|
| `[blocking]` | 必须修改 | 是 |
| `[suggestion]` | 建议改进 | 否 |
| `[question]` | 需要解释 | 视答复而定 |
| `[nit]` | 吹毛求疵，可不改 | 否 |

### 4.5 正反例

| 反例 | 正例 |
|---|---|
| "这里写得不对" | `[blocking] 并发扣款未加锁，两个请求可能双扣；建议用数据库条件更新或分布式锁，参考 xxx` |
| "改一下命名" | `[nit] `amt` 建议改为 `amountInCents`，与金额单位约定一致` |
| 只挑格式问题 | 格式交给工具，人评审设计与边界 |

### 4.6 验收标准

```text
□ 每个 PR 至少 1 名非作者批准，核心模块 2 名
□ 评审意见 100% 有回复（修复或说明）
□ 无未关闭的 [blocking]
□ 评审记录可追溯（PR 内留存结论）
```

## 5. 测试规范

### 5.1 测试分层与比例

| 层级 | 目标 | 占比建议 | 运行时机 |
|---|---|---|---|
| 单元测试 | 逻辑分支、边界 | 70% | 每次提交 |
| 集成测试 | 模块 + 真实依赖 | 20% | 每次 PR |
| 端到端 | 关键用户旅程 | 10% | 合入主干/发布前 |
| 契约测试 | 服务间接口 | 按需 | 接口变更时 |
| 性能基准 | 热点路径回归 | 按需 | 每日/发版前 |

### 5.2 单元测试要求（MUST）

- 结构遵循 Arrange-Act-Assert；
- 用例命名表达"场景 + 预期"，如 `deductCredits_insufficientBalance_throws`；
- 测试必须确定性：不依赖当前时间、随机数、执行顺序、外部网络；
- 外部依赖通过接口 mock；禁止 mock 被测对象自身；
- 一个用例只验证一个行为，失败信息可直接定位。

### 5.3 集成与端到端

- 集成测试可用容器化依赖一键启动；
- E2E 只覆盖核心旅程（登录、下单、支付、核心创作流程），避免全量 UI 断言；
- 不稳定用例（flaky）必须 24 小时内修复或隔离，禁止长期重试掩盖。

### 5.4 Agent / 大模型应用测试

| 测试类型 | 要求 |
|---|---|
| 评测集 | 每次 Prompt/模型变更必须跑固定评测集，记录版本与分数 |
| 回归门禁 | 关键指标（准确率、拒答率、格式合规率）不得下降超过 2% |
| 幻觉与事实性 | 有引用来源的任务必须校验引用可追溯 |
| 工具调用 | 覆盖超时、失败、越权、参数非法四类场景 |
| 成本与延迟 | 记录 token 消耗、首字延迟、P99 延迟 |
| 安全 | 覆盖 Prompt 注入、越权指令、敏感信息套取 |

### 5.5 覆盖率门槛

| 范围 | 要求 |
|---|---|
| 新增/变更代码 | 行覆盖 ≥ 80%，分支覆盖 ≥ 70% |
| 核心资金/权限模块 | 行覆盖 ≥ 90% |
| 整体项目 | 只允许下降 0.05%，持续下降进入专项治理 |

覆盖率不达标不得以"时间紧"豁免；确实无法测试的代码需在 PR 说明并登记技术债。

### 5.6 缺陷分级与修复时效

| 级别 | 定义 | 修复时限 |
|---|---|---|
| P0 | 线上不可用、资损、数据泄露 | 立即止血，24 小时内修复 |
| P1 | 核心功能受损、有绕过 | 3 个工作日 |
| P2 | 非核心功能异常 | 当前迭代 |
| P3 | 体验问题 | 排期处理 |

### 5.7 验收标准

```text
□ 新增代码覆盖率达标
□ CI 单测全绿且无 flaky
□ 关键路径有集成/E2E 覆盖
□ LLM 变更附评测报告
□ 缺陷修复附回归用例
```

## 6. 接口设计规范

### 6.1 REST 约定

| 项目 | 规则 |
|---|---|
| 资源命名 | 名词复数、小写中划线：`/api/v1/order-items` |
| 方法语义 | GET 查询、POST 创建、PUT 全量更新、PATCH 局部更新、DELETE 删除 |
| 状态码 | 200/201/204/400/401/403/404/409/422/429/5xx，禁止一律 200 |
| 错误体 | 统一结构，含 `code`、`message`、`trace_id`、可选 `details` |
| 时间 | ISO 8601 UTC，如 `2026-10-30T08:00:00Z` |
| 金额 | 整数最小单位 + 币种字段 |
| 命名风格 | JSON 字段统一 camelCase 或 snake_case，单仓库内一致 |

统一错误体：

```json
{
  "code": "INSUFFICIENT_CREDITS",
  "message": "积分不足",
  "trace_id": "a1b2c3",
  "details": { "required": 120, "available": 30 }
}
```

**反例**：`{"success": false, "msg": "错误"}`、HTTP 200 包裹业务失败、错误信息带 SQL。

### 6.2 分页、过滤、排序

- 列表必须分页，默认 20，上限 100；
- 大数据量使用游标分页（`cursor` + `limit`），禁止深 offset；
- 过滤与排序字段必须白名单校验，禁止直接拼 SQL。

### 6.3 幂等、重试与超时

- 写接口支持 `Idempotency-Key`，服务端缓存结果 ≥ 24 小时；
- 支付、扣费、发券等资金类操作必须幂等；
- 所有外部调用必须设置连接超时与总超时（建议 3s/10s，按业务调整）；
- 重试仅限幂等操作，采用指数退避 + 抖动 + 最大 3 次；
- 禁止无限重试与无超时调用。

### 6.4 版本与兼容

- URL 版本：`/api/v1/...`；破坏性变更升版本，不原地改语义；
- 向后兼容规则：只增字段不删字段、不改变字段类型、不改变默认语义；
- 废弃字段先标记 `deprecated` 并给出下线日期，观察调用量归零后删除。

### 6.5 gRPC 与事件

- Proto 字段编号一旦分配不得复用，删除字段用 `reserved`；
- 事件必须带 `event_id`、`occurred_at`、`schema_version`；
- 消费端必须幂等，重复投递不产生副作用。

### 6.6 流式与 LLM 接口

| 项目 | 要求 |
|---|---|
| 传输 | SSE 或 WebSocket，事件包含 `start/delta/end/error` |
| 取消 | 客户端断开必须终止后端生成，释放配额 |
| 首字延迟 | 交互式场景 TTFT ≤ 1.5s（P95） |
| 用量 | 响应末尾返回 `usage`（输入/输出 token、费用） |
| 结构化输出 | 使用 JSON Schema 约束，解析失败必须可重试且限次 |
| 长任务 | 提交返回 `task_id`，查询接口提供状态机与进度 |

### 6.7 验收标准

```text
□ OpenAPI/Proto 与实现一致，CI 校验通过
□ 错误码有文档、可枚举、无重复语义
□ 分页、幂等、超时全部落实
□ 契约测试通过，无破坏性变更未声明
□ 流式接口支持取消且有超时
```

## 7. 性能优化规范

### 7.1 性能预算（按场景）

| 场景 | 指标 | 目标 |
|---|---|---|
| 后端接口 | P99 延迟 | 读 ≤ 100ms，写 ≤ 300ms（不含异步任务） |
| 后端吞吐 | 单实例 QPS | 压测达标且 CPU ≤ 70% |
| Web 前端 | LCP / INP / CLS | ≤ 2.5s / ≤ 200ms / ≤ 0.1 |
| 首屏资源 | JS 体积（gzip） | ≤ 200KB，路由级懒加载 |
| 移动端 | 冷启动 | ≤ 2s（中端机），包体增量 ≤ 2MB/版本 |
| LLM 应用 | TTFT / 总时长 | ≤ 1.5s / ≤ 30s（长任务走异步） |
| LLM 成本 | 单请求 token | 有预算上限，超限降级或截断 |

### 7.2 度量与压测

- 所有对外服务必须有延迟、错误率、饱和度三项指标；
- 发版前对核心接口做基准压测，记录基线并纳入回归；
- 性能类 PR 必须附前后对比（P99、内存、CPU、包体）；
- 禁止用"本地感觉很快"作为性能结论。

### 7.3 优化红线（MUST）

1. 禁止循环内远程调用与逐条查询；
2. 禁止无索引的大表扫描与全表 `count`；
3. 禁止在请求链路做同步外部调用（支付回调、模型生成走异步）；
4. 禁止无界队列、无上限线程池/协程池；
5. 禁止一次性加载全量数据到内存；
6. 前端禁止全量引入大型库，按需加载；
7. 缓存必须设置过期与容量上限，禁止永久缓存。

### 7.4 正反例

| 反例 | 正例 |
|---|---|
| 循环里 `findUser(id)` | 批量 `findUsersByIds(ids)` |
| 每次请求实时聚合大表 | 预聚合 + 增量更新 |
| 列表页一次返回 5000 条 | 游标分页，每页 20 |
| 模型调用无超时 | 设置超时、重试上限与降级策略 |

### 7.5 验收标准

```text
□ 核心接口达到性能预算
□ 压测报告归档，含基线与本次对比
□ 无性能红线违规
□ 前端性能预算在 CI 中检查
```

## 8. 安全规范

### 8.1 认证与授权（MUST）

- 所有非公开接口必须鉴权，服务端校验，不信任前端隐藏；
- 权限按"最小权限"授予，资源级校验（防越权 ID 遍历）；
- 会话令牌短期有效 + 可撤销；敏感操作二次验证；
- 服务间调用使用独立凭证，禁止共用管理员密钥。

### 8.2 输入输出与注入

- 所有外部输入在边界校验类型、长度、范围、枚举；
- SQL 使用参数化查询，禁止字符串拼接；
- 命令执行禁止拼接用户输入；模板渲染默认转义；
- 上传文件校验类型、大小、内容，存储与执行隔离。

### 8.3 密钥与配置

- 密钥只从密钥管理服务/环境变量注入，禁止入库、入包、入前端产物；
- 不同环境独立密钥，生产密钥最小范围授权；
- 密钥泄露视为 P0，立即轮换并审计调用记录。

```ts
// 反例
const apiKey = 'sk-live-9f8a...';

// 正例
const apiKey = process.env.OPENAI_API_KEY;
if (!apiKey) throw new ConfigError('OPENAI_API_KEY missing');
```

### 8.4 数据隐私

- 日志、埋点、错误上报必须脱敏（手机号、身份证、地址、Token、Prompt 原文）；
- 数据按敏感级别分类，跨域传输加密；
- 用户数据删除请求必须在约定时限内完成并留痕；
- 测试环境禁止使用生产真实数据。

### 8.5 依赖与供应链

- 锁文件必须提交，构建可复现；
- 新增依赖需评审：维护状态、许可证、体积、已知漏洞；
- CI 每次构建执行依赖漏洞扫描，高危阻塞发布；
- 禁止引入来源不明的包与脚本。

### 8.6 Agent / LLM 特有安全

| 风险 | 要求 |
|---|---|
| Prompt 注入 | 系统提示与用户输入隔离；工具调用参数白名单校验 |
| 越权工具调用 | 工具按最小权限授权，写操作需二次确认或人工审批 |
| 数据外泄 | Prompt 中禁止拼接未脱敏的敏感数据；限制上下文长度 |
| 输出风险 | 输出经过内容安全过滤，禁止直接执行模型生成的代码/命令 |
| 成本滥用 | 按用户/租户限流与配额，异常用量告警 |
| 模型与供应商 | 记录模型版本、区域、数据留存策略，满足合规要求 |

### 8.7 漏洞响应

| 级别 | 响应 | 修复 |
|---|---|---|
| 严重（可导致数据泄露/资损/ RCE） | 立即止血 | 24 小时内 |
| 高危 | 当日确认 | 3 个工作日内 |
| 中危 | 排期 | 当前迭代 |

安全漏洞禁止提交公开 issue，走私密渠道并限制知悉范围。

### 8.8 验收标准

```text
□ 鉴权与资源级越权测试通过
□ 无硬编码密钥，密钥扫描零命中
□ 依赖漏洞扫描无高危
□ 日志脱敏抽查通过
□ LLM 注入与越权用例通过
```

## 9. 部署发布规范

### 9.1 环境与配置

| 环境 | 用途 | 数据 |
|---|---|---|
| dev | 本地/联调 | 模拟数据 |
| staging | 预发验证 | 脱敏数据 |
| prod | 生产 | 真实数据 |

- 配置与代码分离，同一构建产物 promote 到各环境；
- 禁止在服务器手工改配置，配置变更走版本控制与流水线；
- 环境差异通过配置项显式声明，禁止 `if (env === 'prod')` 散落代码。

### 9.2 CI/CD 门禁链（MUST）

```text
1. 代码扫描：格式、lint、静态分析、密钥扫描
2. 单元测试 + 覆盖率检查
3. 构建与制品签名（可复现构建）
4. 依赖漏洞扫描（高危阻塞）
5. 集成/契约测试
6. 数据库迁移校验（可回滚、无锁表风险）
7. 部署到 staging + 冒烟测试
8. 灰度发布 + 指标观察
9. 全量发布
```

### 9.3 数据库变更

- 采用 **expand → migrate → contract** 三步，禁止一次性破坏性变更；
- 大表加索引、改字段必须评估锁表时间，使用在线 DDL；
- 每个迁移必须有回滚脚本或明确"不可回滚"说明与补偿方案；
- 数据修改变更必须有备份与审计。

### 9.4 发布策略

- 默认灰度：1% → 5% → 25% → 100%，每阶段观察核心指标；
- 关键功能使用 feature flag，支持按租户/用户维度开关；
- 灰度期间监控错误率、P99、业务转化，异常自动暂停；
- 发布窗口避开业务高峰，紧急发布走审批通道。

### 9.5 回滚

- 回滚时间目标 ≤ 10 分钟；
- 回滚方案在发布前写好（代码回滚、开关关闭、数据补偿）；
- 数据变更不可回滚时，必须有降级读路径；
- 每次回滚后 48 小时内输出复盘。

### 9.6 Agent / 模型发布

- Prompt、模型、工具定义分别版本化，任一变更都可独立回滚；
- 上线前跑评测集与影子流量对比；
- 记录模型版本与参数快照，保证线上问题可复现；
- 成本与延迟纳入发布观察指标。

### 9.7 验收标准

```text
□ 制品由流水线构建，无手工发布
□ 灰度阶段指标达标
□ 回滚演练每年至少一次
□ 迁移脚本可回滚且经过评审
□ 发布记录含版本、变更、负责人、回滚点
```

## 10. 文档维护规范

### 10.1 README（每个仓库必备）

```text
□ 项目职责与边界
□ 架构图与关键依赖
□ 本地启动步骤（可复制执行）
□ 配置项说明（含默认值与影响）
□ 测试与发布方式
□ 监控指标与告警入口
□ 负责人与值班方式
```

### 10.2 API 文档

- 由代码/注解自动生成（OpenAPI、Proto），禁止手写第二份；
- 每个接口包含：用途、鉴权、参数、错误码、示例、限流；
- 文档随代码同 PR 更新，CI 校验文档与实现一致。

### 10.3 架构决策记录（ADR）

重大决策（框架选型、数据模型、协议、外部依赖）必须写 ADR：背景、方案对比、结论、影响与后续动作。ADR 与代码同仓维护，编号递增。

### 10.4 Runbook

每个线上服务必须有 Runbook：常见故障现象、排查步骤、止血手段、升级路径、联系人。

### 10.5 CHANGELOG

- 面向使用者描述行为变化，不粘贴 commit 列表；
- 分类：新增、变更、修复、破坏性变更；
- 每次发布必须更新，并与 tag 对应。

### 10.6 验收标准

```text
□ README 可按步骤跑通
□ API 文档由代码生成且 CI 校验
□ 重大决策有 ADR
□ 线上服务有 Runbook
□ CHANGELOG 与发布记录一致
```

## 11. 落地与治理

### 11.1 门禁矩阵

| 阶段 | 门禁 | 执行方 |
|---|---|---|
| 提交前 | 格式化、lint、单测（本地钩子） | 开发者 |
| PR | 评审批准、CI 全绿、覆盖率、安全检查 | 平台 |
| 合入 | 主干同步、Squash、线性历史 | 平台 |
| 发布 | 制品签名、迁移校验、灰度指标 | 平台 + 值班 |
| 线上 | 监控告警、错误预算、回滚预案 | 值班 |

### 11.2 度量指标（按季度看板）

- PR 平均体积与评审时长；
- 新增代码覆盖率与 flaky 用例数；
- 线上 P0/P1 事故数与平均恢复时间；
- 高危漏洞平均修复时长；
- 技术债存量与关闭率；
- LLM 应用的单位成本与评测分数趋势。

### 11.3 治理机制

1. 规范变更走提案（issue + 影响面 + 迁移方案），公示一周后生效；
2. 每季度评审一次门禁有效性，过严导致绕过的规则要调整；
3. 新增规则必须同时提供工具支持或检查清单，否则不发布；
4. 事故复盘必须产出至少一条可自动化检查项。
